# Frontend authentication setup (T4a)

Before testing with a real project, a human administrator must enable email confirmation for email/password signup in Supabase Auth and allowlist the exact same-origin callback `https://<your-app-origin>/auth/confirm` (substitute the actual app origin). Configure only `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` in a private deployment environment. Do not put real values in source, examples, logs or this README. No provider setting has been changed by this work.

Signup requests confirmation for patient, professional and institution. A validated account-type preference alone may be kept in browser sessionStorage as an untrusted UI hint; it is not an identity, role, or saved profile, and can be unavailable or stale. An unexpected signup session is signed out locally and treated as a configuration failure: email confirmation must be enforced by the provider. The callback performs one explicit PKCE exchange in the same browser, then checks the current confirmed identity. An expired link or a different browser requires email/password sign-in. The onboarding screen is a confirmed-email handoff placeholder, **not** a saved profile. Browser SDK session persistence is not HttpOnly; its lifetime is provider-defined. No clinical authorization is inferred from it. Protected API/profile integration belongs to T4b.
